**Revision note (2026-07-30, Error-code taxonomy batch)**: T016 previously marked "no dedicated taxonomy file exists." That framing was only partially accurate: `backend/src/lms/access.types.ts` already provided a well-centralized `AccessDenialReason` (16 values) / `EntitlementStatus` taxonomy for the access-DENIAL family, consumed by the single `evaluateCourseAccess` → `evaluateModuleAccess` → `evaluateLessonAccess` pipeline every endpoint reuses. What was genuinely missing — and what this batch adds — is the **business-rule-rejection** family (capacity/attempt-limit/eligibility codes), which existed only as scattered, undeclared string literals with no shared reference: `COURSE_FULL` duplicated verbatim across `enrollment.service.ts` and `wishlist.service.ts`; `QUIZ_ATTEMPT_LIMIT_REACHED`/`ASSIGNMENT_ATTEMPT_LIMIT_REACHED` each defined once with no shared source of truth; and certificate ineligibility, which had no code at all, only a message. `lms-error-codes.ts` now declares `LMS_BUSINESS_RULE_CODES` (`COURSE_FULL`, `QUIZ_ATTEMPT_LIMIT_REACHED`, `ASSIGNMENT_ATTEMPT_LIMIT_REACHED`, `CERTIFICATE_NOT_ELIGIBLE` — the last a genuinely new, additive code) and re-exports `AccessDenialReason`/`EntitlementStatus` rather than duplicating them, and every call site (`enrollment.service.ts`, `wishlist.service.ts`, `certificate.service.ts`, `quiz-attempt.service.ts`, `assignment-submission.service.ts`) now references it via a typed local (`const code: LmsBusinessRuleCode = '...'`) instead of an unchecked string literal — a deliberately low-risk refactor that changes none of the existing wire-level string values, so no existing frontend detection call site (e.g. `CourseDetailPage.tsx`'s `details.code === 'COURSE_FULL'` check) needed to change. The top-level HTTP `error.code` convention (`ERROR_CODES.FORBIDDEN`/`VALIDATION_ERROR`/`CONFLICT`) is unchanged; this taxonomy organizes the specific, nested `details.code`/`details.reason` vocabulary clients actually branch on.

While auditing every access-denial call site for this taxonomy, a genuine pre-existing bug was found and fixed: `lesson-resource.service.ts`'s private `assertLessonAccessibleForResources` helper (added in the immediately-prior Downloadable Resource Catalog batch) silently dropped `reason`/`detail` via a bare `throw AppError.forbidden(access.message)`, unlike every other lesson-access-denial call site in the codebase (`bookmark.service.ts`, `learner-note.service.ts`, `student-lms.controller.ts`, `progress.service.ts`), which all correctly propagate `{ reason: access.reason, ...access.detail }` — meaning a client could not branch on a specific denial reason for resource-access denials, defeating FR-125's own stated purpose for that one surface. Fixed by extracting a single shared `assertLessonContentAccessible(userId, lessonId)` into `access-evaluator.service.ts` itself (the module that already owns `evaluateLessonAccess`), consumed by `bookmark.service.ts`, `learner-note.service.ts`, and `lesson-resource.service.ts` in place of their three near-duplicate private helpers — preventing this exact class of drift from recurring. (`student-lms.controller.ts`'s and `progress.service.ts`'s own inline copies were left as-is: both already behave correctly, and consolidating them would only add a redundant lesson fetch with no bug to fix.)

This batch built FR-028/029 end-to-end: `WaitlistEntry` model + `WaitlistEntryStatus` enum (migration `20260729184840_spec004_waitlist`) and `waitlist.service.ts`. A course with `Course.enrollmentLimit` set that is at capacity accepts a waitlist join instead of direct enrollment (rejects joining an uncapped course or one with open seats, and rejects a duplicate join or joining a course the learner is already enrolled in). When a seat frees, the next-priority (monotonic, first-come-first-served) WAITING entry is OFFERED a REAL, time-limited reservation (a 48-hour default window, since FR-029 does not name an exact duration) — `enrollment.service.ts`'s capacity check now counts every live OFFERED entry against `enrollmentLimit` too, so a competing direct-enroll attempt correctly still sees the course as full while an offer is outstanding (verified live: a third party's direct-enroll attempt returns 409 `COURSE_FULL` while the offer stands). An unclaimed, expired offer passes automatically to the next-priority entry, evaluated at READ time (`sweepAndAdvanceWaitlist`, called on both seat-release and every waitlist read) — this codebase's established "no background job scheduler exists" convention, not a fabricated cron job. Only `revokeEnrollment` (the sole enrollment-lifecycle transition with a real caller today) triggers the sweep; the hook lives at `transitionEnrollment`'s single shared choke point so `CANCELLED`/`EXPIRED` will correctly trigger it too the moment either becomes a real code path. Claiming an offer reuses the existing, already-tested `selfEnroll` (the waitlist is purely a capacity gate, not a distinct entitlement path).
