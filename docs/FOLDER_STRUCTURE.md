# CoachX — Folder Structure Guide

## Top level

```
coachx/
├── frontend/          Member-facing web app (React + Vite + TS + Tailwind)
├── backend/           REST API (Node.js + Express + TypeScript)
├── admin/             Internal admin portal (React + Vite + TS + Tailwind)
├── mobile/             Mobile app (Flutter)
├── shared/             TypeScript types/constants/utils shared by
│                        frontend, backend, and admin
├── database/           Prisma schema, migrations, and seed scripts
│                        (single source of database truth)
├── infrastructure/      Docker, docker-compose, and deployment config
├── docs/                Project documentation (this folder)
├── scripts/             Repo-wide setup/build/dev shell scripts
├── .github/workflows/   CI pipeline
├── specs/               Spec-Kit feature specifications (001-073) —
│                        the design source every feature is built from
├── package.json         npm workspaces root
└── README.md
```

`specs/`, `document 1/`, `document 2/`, `.specify/`, `CLAUDE.md`, and
`PRD_SUMMARY.md` are the pre-existing specification/PRD artifacts this
implementation is built from — they are not application code and are
left untouched by the application scaffold.

## `backend/`

```
backend/
├── src/
│   ├── config/          Validated environment/config loader (env.config.ts)
│   ├── database/         Prisma client singleton (connect/disconnect,
│   │                      health check), transaction wrapper, retry
│   │                      classification, error normalization,
│   │                      pagination, audit-event repository,
│   │                      idempotency service — see docs/database/
│   │                      ARCHITECTURE.md §3 for the full module map
│   ├── middlewares/       error-handler, not-found, request-logger,
│   │                       request-id (correlation ID)
│   ├── routes/
│   │   ├── v1/            Version-1 API routes (health, readiness, ...)
│   │   └── index.ts        Mounts each API version under its own prefix
│   ├── controllers/        Route handler functions
│   ├── utils/               logger (+ redact), AppError, asyncHandler
│   ├── types/                Express Request augmentation (req.id)
│   ├── app.ts                 Express app assembly (no listen())
│   └── server.ts                Process entrypoint, DB connect/disconnect,
│                                  graceful shutdown
├── tests/
│   ├── contract/          Full-app Supertest tests (health, readiness,
│   │                       404, error handler, request-id)
│   └── unit/                Isolated-module tests (redact, env parsing,
│                              logger pipeline)
├── jest.config.js
├── .env.test              Committed — safe, test-only, isolated config
├── package.json
└── tsconfig.json
```

New business modules add their own `*.controller.ts` / `*.routes.ts` /
service files and register a router in `src/routes/v1/index.ts` — that
file is the only integration point the rest of the app needs to know
about.

## `frontend/` and `admin/`

Both apps share the same internal shape (they are separate Vite
projects, not one app with role-based rendering):

```
src/
├── api/           Axios instance + typed API call functions
├── components/
│   ├── layout/     App shell (Header/Footer/MainLayout, or Sidebar/Topbar/AdminLayout)
│   └── system/     Foundation-only diagnostic screens (not business pages)
├── config/         Runtime env accessor (env.ts)
├── context/        React context providers (theme.context.tsx)
├── hooks/          Shared hooks (frontend only, so far)
├── routes/         Router configuration (router.tsx)
├── styles/         Tailwind entrypoint (index.css)
├── types/          App-local type augmentations
├── utils/          Small framework-free helpers (cn.ts)
├── App.tsx
└── main.tsx
```

Business feature UI is added under `components/` (or a future
`features/<domain>/` subfolder, introduced when the first real feature
is implemented) and registered as a route in `routes/router.tsx`.

## `mobile/`

```
mobile/lib/
├── app/
│   ├── app.dart            Root MaterialApp (theme + routing)
│   └── widgets/             Foundation-only diagnostic widgets
├── core/
│   ├── config/              Compile-time config (env_config.dart)
│   ├── network/              ApiClient + shared network types
│   ├── routing/               Named-route table (app_router.dart)
│   └── theme/                  Material 3 theme
└── main.dart
```

Standard Flutter platform folders (`android/`, `ios/`, `test/`) are
generated by `flutter create` and left at their default location.

## `shared/`

```
shared/src/
├── types/        ApiResponse envelope, HttpStatus enum, HealthCheckResult, ...
├── constants/     API_VERSION, ERROR_CODES, pagination defaults
└── utils/          buildSuccessResponse / buildErrorResponse
```

Only cross-cutting, domain-agnostic primitives live here. Business
domain types (User, Course, Membership Tier, ...) belong to the feature
that owns them and are defined in that feature's own package/module —
`shared/` is not a dumping ground for every type in the system.

## `database/`

```
database/
├── prisma/
│   ├── schema.prisma     Shared TECHNICAL models only (AuditEvent, IdempotencyKey — Phase 3).
│   │                     Business-domain models belong to their own future feature, not here.
│   └── migrations/        Generated by `prisma migrate dev` / `prisma migrate diff`
└── seeds/
    └── index.ts            Seed runner entrypoint (still no-op — no seed data defined yet;
                             has a production-safety guard as of Phase 3)
```

See `docs/database/` for the full database architecture documentation
(schema ownership, migrations, seeding, multi-tenancy strategy,
auditability, transactions/idempotency, testing, and open decision
gates) — read that folder, not just this summary, before adding any new
model.

## `infrastructure/`

```
infrastructure/
├── docker/
│   ├── backend.Dockerfile
│   ├── frontend.Dockerfile
│   ├── admin.Dockerfile
│   └── nginx.spa.conf       Shared Nginx config for the two static apps
├── docker-compose.yml        Full stack (Postgres + backend + frontend + admin)
└── docker-compose.dev.yml    Postgres only, for local `npm run dev`
```
