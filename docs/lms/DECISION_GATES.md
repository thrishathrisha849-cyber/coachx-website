# LMS Decision Gates and Known Limitations (Phase 6 Part 1)

Status: this file is **implemented-now** as a record; every row is, by
definition, not yet fully resolved. Same format as
`docs/database/DECISION_GATES.md` / `docs/auth/DECISION_GATES.md` /
`docs/public-site/DECISION_GATES.md`.

| # | Gate | Current state | Why deferred | Future Feature Owner / Re-check trigger |
| --- | --- | --- | --- | --- |
| 1 | **Admin frontend LMS UI** | **Not built. Backend/API is complete; the admin UI itself is deferred.** | The `admin/` app has **zero authentication wiring** anywhere — no login page, no token storage, no `Authorization` header attachment (`admin/src/api/client.ts`'s own comment: "Admin-role auth-token attachment belongs to the authentication feature module and is added in a later implementation phase" — a pre-existing Phase 1 gap, not LMS-specific). Building course-management screens that call `authenticate`-gated admin APIs would either be non-functional (no way to actually authenticate) or would require inventing admin login/session handling as an undocumented side effect of an LMS phase — a cross-cutting concern affecting EVERY future admin module, not just LMS, and explicitly not requested by this phase's brief. The brief itself allows this: "If frontend integration cannot be completed safely within Part 1, finish backend/API/data architecture completely and document the admin-UI remainder as an explicit Part 1 limitation. Do not falsely claim frontend completion." | A dedicated admin-authentication frontend task (building on Phase 4's already-complete backend auth) — once that exists, the admin LMS screens described in the brief (course list/create/edit, category management, module reorder, instructor assignment, status controls) can be built against the already-complete, already-tested admin API surface with no backend changes needed |
| 2 | `PRIVATE` course visibility | Not modeled — `CourseVisibility` only has `PUBLIC`/`UNLISTED` | Meaningless without Part 2's `Enrollment` model to answer "private to whom" | Phase 6 Part 2, once `Enrollment` exists |
| 3 | Idempotency-key protection for LMS writes | Not wired in for any Part 1 endpoint | Slug uniqueness already provides safe conflict semantics for the classic double-submit case; wiring the mechanism into every create/reorder/status-change endpoint speculatively would be over-engineering with no observed problem to justify it | Revisit if a real double-submit bug report ever surfaces in production |
| 4 | `Course.version` optimistic-concurrency enforcement | Field exists, incremented on update, but not yet CHECKED against a caller-supplied expected version | No concurrent-edit UI exists yet to generate the conflict this would need to detect (see gate #1 — no admin UI at all yet) | Once an admin edit UI exists (gate #1) |
| 5 | Category hierarchy depth limit | Not enforced — `assertParentValid()` prevents self-parenting and cycles but allows arbitrarily deep nesting | No product requirement named a specific max depth; an arbitrary cap now would be a guess | A deliberate product decision on max depth, if deep nesting ever becomes an actual UX problem |
| 6 | Course rich-text format | Plain HTML string (sanitized at render time via the existing DOMPurify allowlist), not markdown | Matches the CMS `TEXT` block's own established choice — no markdown parser exists anywhere in this codebase yet | If a markdown authoring path is ever added platform-wide, it must render through the same `sanitizeRichText()` after conversion, not bypass it |
| 7 | Course SEO fallback behavior | `title`/`shortDescription` are the accepted fallback when `seoTitle`/`seoDescription` are unset — never blocks publishing | Matches `docs/public-site/SEO.md`'s established "fallback, not hard failure" pattern for CMS pages | — |
| 8 | Public course-preview behavior for a DRAFT course | Not implemented — LMS has no preview-token mechanism analogous to CMS `Page.previewTokenHash` | Not requested by the Part 1 brief; the instructor-scoped API already lets an assigned instructor see their own DRAFT course directly (no public preview link needed for that use case) | If a "share a draft course preview link with someone who isn't an assigned instructor" use case is ever named |
| 9 | Instructor publishing permission | Resolved for Part 1: `course_instructor` does NOT hold `course.publish` — see `docs/lms/RBAC.md` | — (this is a resolved decision, kept here for visibility since the brief listed it as an open gate to resolve) | Revisit if product direction changes to allow self-publish for trusted instructors |
| 10 | Admin UI depth (if/when built) | N/A — see gate #1 | — | — |
| 11 | Course ordering / featured ranking on the discovery page | `isFeatured` boolean + `sort=featured` (featured-desc, then newest) — no separate manual "ranking" field | The brief's suggested field list didn't include a distinct ranking/weight field beyond `isFeatured`; inventing one without a named requirement would be speculative | If a manual "pin to top" ranking requirement is ever named |
| 12 | CDN / media ownership (thumbnail/cover/trailer upload) | Not implemented — these are plain URL string fields, no upload/storage pipeline | No media/upload infrastructure exists anywhere in this codebase yet (same gap 004/plan.md itself flags as `NEEDS CLARIFICATION` for video/CDN vendor) | A dedicated media-upload feature, platform-wide (not LMS-specific) |
| 13 | React Router v6 security-upgrade timing | Unchanged from Phase 5's own finding (`docs/public-site/DECISION_GATES.md` doesn't have this row — it was found in the Phase 5 Part 3 final report, not a doc row) — 2 moderate CVEs, fix requires a v6→v7 major upgrade | Pre-existing since Phase 1, unrelated to LMS; this project's established discipline avoids unilateral forced major upgrades | A deliberate, scheduled dependency-upgrade task |
| 14 | `cacheControl` middleware housed under `backend/src/cms/` but reused by `lms.routes.ts` | Works correctly (it's genuinely generic, CMS-agnostic code) but is a minor ownership/discoverability smell — a developer looking in `lms/` for all of LMS's own middleware won't find it there | Introduced to avoid duplicating an identical file; the reuse is documented in `docs/lms/ARCHITECTURE.md` | A future cleanup: hoist to `backend/src/middlewares/cache-control.middleware.ts` or a shared `common/` folder, updating both CMS's and LMS's route files to import from there |
| 15 | `CourseDetailPage.tsx` frontend test coverage | No dedicated test file (unlike `CourseListPage.tsx`, which has 3 tests) | Time-boxed prioritization within an already very large phase; the page follows the identical, already-tested pattern `BlogDetailPage.tsx` uses (untested itself, for the same reason) | A follow-up test-coverage pass |
| 16 | LMS seed data (sample categories/courses for local development) | Not created — no `database/seeds/lms.seed.ts` | Not explicitly requested by the brief; Phase 5's `cms.seed.ts` exists because Part 1 of that phase explicitly needed seeded pages for the frontend to render against, whereas LMS Part 1's frontend can be verified against test-created data | If local-dev/demo seed data is ever explicitly requested |
